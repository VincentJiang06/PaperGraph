# WORKFLOW — topic to paper

This is the driver skill for a coding-agent Orchestrator. It turns one topic into a finished paper
through parallel research, two deterministic in-loop gates, and a separate held-out eval.

The host coding agent supplies native subagents. PaperGraph does not call a model API and does not
require an API key.

## Quality layers

- **DIVERGENCE** (`gates/divergence.md`) checks author-side position coverage and the strongest
  objection. Metric: coverage and engagement.
- **RIGOR + TRACEABILITY** (`gates/rigor.md`) re-executes data transforms and verifies saved source
  excerpts. Metric: reproduce-rate.
- **HELD-OUT EVAL** (`eval/EVAL.md`) independently re-derives the field map and runs blind judges.
  It is the release decision, not an in-loop optimization target.

Both gates run on every paper. Both green means candidate; only a complete held-out eval can mean
`SHIP`.

## Per-paper files

```text
runs/<slug>/
  paper.md          shared artifact; Orchestrator is the only writer
  positions.md      author-side position map; Orchestrator merges cartography
  claims.tsv        one row per empirical claim; Orchestrator merges grounders
  transforms/       one deterministic script per kind=data claim
  metrics/          one produced JSON value per kind=data claim
  sources/          one saved source text per kind=source claim
  dvc.yaml          DVC stages for data claims; optional for source-only papers
  dvc.lock          generated data provenance
  gate_report.md    generated by the two gate scripts
```

`claims.tsv` is tab-separated with this exact header:

```text
claim_id	kind	claim_text	value	raw_ref	transform_or_source	reproduced
```

The exact position, claim, transform, and pass contracts are defined in `gates/*.md`.

## The loop

1. **Scope.** Convert the topic into one thesis question, explicit in/out boundaries, and exactly
   one `field-weight: humanities|mixed|science` line at the top of `paper.md`. State what evidence
   could overturn or materially narrow the thesis.

2. **Map.** Dispatch one Cartographer with the thesis and scope only. It maps the field's serious
   positions and one strongest objection using the `positions.md` interface. The Orchestrator
   validates and writes the map.

3. **Diverge in parallel.** Dispatch one Advocate per position plus one Adversary concurrently.
   Each Advocate receives exactly one position block and returns its strongest case, best evidence,
   and the fairest answer available to the thesis. The Adversary returns the strongest thesis-level
   objection and the evidence that would make it succeed. The Orchestrator distils these returns;
   workers do not edit `paper.md`.

4. **Ground in parallel.** Identify every empirical assertion the argument depends on. Assign a
   stable `claim_id`, then dispatch one ClaimGrounder per claim concurrently:

   - `kind=data`: produce a deterministic `transforms/<claim_id>.py`, the raw-data reference, and a
     proposed ledger row. The transform writes `metrics/<claim_id>.json`.
   - `kind=source`: save `sources/<claim_id>.txt`, provide the real URL, and use an exact excerpt as
     the ledger `value` so the offline check is meaningful.

   ClaimGrounders have disjoint IDs and paths. The Orchestrator validates and merges rows into
   `claims.tsv` and wires data claims into `dvc.yaml`.

5. **Draft.** The Orchestrator writes `paper.md` from the mapped and grounded argument. Every
   empirical sentence cites its `claim_id`; every engaged position is tagged as required by the
   divergence interface. Worker reports are research inputs, not prose to paste wholesale.

6. **Run both gates.** Execute from the repository root:

   ```bash
   python3 gates/rigor_gate.py runs/<slug>
   python3 gates/divergence_gate.py runs/<slug>
   ```

   For each failure, revise the responsible artifact: missing position -> engage or honestly
   exclude it; ungrounded claim -> add provenance or remove it; mismatch -> fix the transform or
   claim; unsupported quote -> re-fetch or remove it. Repeat steps 4-6 until both gates pass.

7. **Evaluate the candidate out of loop.** Freeze a candidate snapshot, then follow
   `eval/protocol.md`: derive or select the literature answer key and dispatch all held-out judges.
   EvalAdvocates (one per answer-key position), EvalAdversary, ClaimAuditor, and at least three
   Referees run independently and in parallel. None may use gate results or the author's
   `positions.md` as ground truth. Aggregate only after all required outputs exist, then run the
   eval harness.

8. **Ship or revise.** `SHIP` only when the complete D1-D5 evaluation satisfies `eval/EVAL.md`.
   Missing judge outputs are incomplete, never a pass. On `REVISE`, change the paper or workflow,
   re-run the in-loop gates, and evaluate a later candidate; never edit the held-out key or rubric
   to admit the paper.

## Parallelism contract

```text
scope -> cartographer
      -> [Advocate P1 | Advocate P2 | ... | Adversary] -> orchestrator merge
      -> [Grounder C1 | Grounder C2 | ...]             -> orchestrator merge
      -> draft + deterministic gates
      -> [EvalAdvocates | EvalAdversary | ClaimAuditor | Referee x3+] -> aggregator
```

Parallel tasks must have disjoint IDs, bounded inputs, and one declared output. Only the
Orchestrator writes shared author artifacts. Only the EvalAggregator writes the merged eval verdict.
Chat responses are not durable state until validated and merged.

## Bounded task prompts

- **Cartographer:** "Given only this thesis and scope, map the real schools, lenses, and serious
  objections in the field. Return the exact `positions.md` blocks. Do not optimize for the draft."
- **Advocate:** "Act as the strongest proponent of position `<P-id>`. Return its best argument,
  strongest evidence with source, and what a fair answer must concede. Do not edit shared files."
- **Adversary:** "Construct the strongest objection to this thesis. State what must be true for it
  to succeed and which evidence bears on that test. Do not merely negate the thesis."
- **ClaimGrounder:** "Ground only `<claim_id>`. Return one proposed ledger row and its assigned
  transform or saved-source artifact. Do not touch any other claim or shared file."

Held-out judge prompts and output fields are defined only in `eval/protocol.md`; do not copy their
rubric into the author loop.

## Stop rules

- Stop author revision only when both gates pass.
- Stop evaluation only when every required independent output exists and validates.
- Stop the project with `SHIP` only on a complete held-out pass.
- If the gated arm does not beat the freehand arm on the held-out scorecard, report that result
  honestly; do not add more framework to hide it.
