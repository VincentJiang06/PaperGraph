# PaperGraph — gated paper workflow

Everything before this is archived (`archive/pre-reset-2026-07-09/`) and treated as a
failed attempt. Both the old PaperGraph and nodify made the same mistake: they built a
**framework** (a tree/graph of claims + a CLI + schemas) and hoped the *structure* would
make the reasoning better. Four rigorous ablations said it doesn't. We stop building
frameworks.

## What we learned to copy (karpathy/autoresearch)
- **Deliberately tiny.** "Only three files that matter." No framework, no schemas, no tree.
- **The agent iterates on ONE artifact** (`train.py`); the human writes a **markdown
  "super-lightweight skill"** (`program.md`). Intelligence = agent + instructions + loop.
- **An objective, RE-RUNNABLE gate + a keep/discard loop.** Rigor comes from a *metric you
  can re-run* (`val_bpb`), not from ceremony. Try → measure → keep-if-better → repeat.
- **Auditable via a dead-simple ledger** (`results.tsv`).

## The goal (unchanged from the very beginning)
A workflow that takes a **topic → a finished paper**, and specifically fixes the two ways
these papers are bad:
- **(Humanities) 观点不够发散** — the argument is one-sided / shallow; it doesn't explore
  the real space of positions and objections.
- **(Science / data-cleaning) 证明不够严密、不可回溯** — empirical claims aren't verifiable
  or reproducible; you can't get from a number in the paper back to the raw data and the
  step that produced it.

**Insight:** these are not "write better prose" problems. They are two places where an
**objective, re-runnable gate** can force quality — exactly like `val_bpb`. So we build
two gates and a loop, and almost nothing else.

## The design: paper = artifact, two gates, one loop

The **paper (markdown) is the artifact** the agents iterate on (like `train.py`). A markdown
**WORKFLOW.md** is the program.md-style skill. The two author-facing gates provide the fast
in-loop signal, and a separate held-out eval judges whether the result is actually ready. A ledger
is the audit trail. **No product CLI, application schema layer, or claim tree.** The few boundary
file formats used by gates and eval agents are explicit contracts, not a framework.

> **Both gates run on EVERY paper.** They are two quality dimensions of ONE workflow, not
> two pipelines / two paper types. A humanities paper still needs traceable evidence; a
> science paper still needs divergent interpretation. The field only shifts the *weight*
> and thresholds (humanities → divergence-heavy; science → rigor-heavy) — both always run.

### Gate 1 — DIVERGENCE (every paper; dominant in humanities), objectively measured
Divergence is generated by fan-out and enforced by a coverage gate:
1. **Map the position-space.** An independent "cartographer" agent maps the *field's* space
   of legitimate positions / lenses / strongest objections on the thesis — not the paper's.
   This is the ground truth of what "divergent enough" means for this topic.
2. **Fan out to steelman.** Parallel "advocate" agents each argue a *different* position to
   its strongest form; an "adversary" builds the single strongest objection to the thesis.
3. **Score coverage (the gate).** Measure the fraction of the position-space the paper
   actually *engages with a real argument* (not a strawman). **FAIL** if coverage < K, or
   the strongest objection is unaddressed. The loop revises the paper to engage the missing
   positions until it passes. Divergence is produced + enforced, not hoped for.
   *Metric: position-space coverage % + strongest-objection-engaged (yes/no).*

### Gate 2 — RIGOR + TRACEABILITY (every paper; dominant in science), executably verified
Every empirical claim must be **reproducible from raw data by a re-runnable transform** —
and the gate **re-runs it** (exactly like re-running `train.py` and checking `val_bpb`):
1. **Provenance record per empirical claim:** `{claim, raw_data_ref, transform_script,
   produced_value, output_hash}`.
2. **The gate RE-EXECUTES the transform** on the raw data and checks the produced value
   matches the claim within tolerance. **FAIL** if a number can't be reproduced from logged
   raw data + a logged script.
3. **Data-cleaning is versioned + auditable:** every cleaning/analysis step is a logged,
   re-runnable script; the ledger records each transform + its output hash. A reviewer can
   re-run the whole pipeline from raw data → every number in the paper.
   *Metric: reproduce-rate = fraction of empirical claims whose number re-executes.*

### Two quality layers — never conflate them

The author creates `positions.md`, `claims.tsv`, and the paper while seeing both gate rules. The
gates can therefore enforce a useful structural floor, but they cannot be the final quality judge.

- **In-loop gates (`gates/`):** cheap, deterministic, and run on every revision. Both must pass.
- **Held-out eval (`eval/`):** independent, literature-anchored, and run only on a candidate. Its
  agents are blind to the author's scaffolding where independence matters. It decides `SHIP` or
  `REVISE` under `eval/EVAL.md`.

Both gates green means **candidate**, not finished. A paper cannot ship with a partial held-out
panel, even when the mechanical eval screen happens to return a favorable result.

### The loop (topic → paper)
```
scope topic
→ DIVERGENCE: map position-space → fan out advocates + adversary → draft the argument
→ RIGOR: for each empirical claim, write the reproduce-script → run gate 2
→ assemble prose from the (now covered + reproduced) argument
→ run BOTH gates → targeted revision on any failure → repeat until both pass
→ run the held-out eval against an independently derived literature key
→ REVISE the paper/workflow on failure; SHIP only on a complete eval pass
```

### Minimal control surface (autoresearch-style)
```
WORKFLOW.md              — the driver skill (the loop + how agents are dispatched)   [program.md]
gates/divergence.md      — how to map the position-space + score coverage
gates/rigor.md           — how to build reproduce-scripts + the re-execution gate
eval/EVAL.md             — held-out quality policy; never optimized in-loop
eval/protocol.md         — independent judge handoff contract
runs/<paper>/paper.md    — the artifact the agents iterate on                        [train.py]
runs/<paper>/claims.tsv  — audit trail: claim → source → transform → reproduced?      [results.tsv]
runs/<paper>/transforms/ — the re-runnable data-cleaning/analysis scripts (science)
```

### Why this is different from everything we archived
- It optimizes the **two real quality axes** (divergence, rigor) with **objective gates**,
  not a data structure. The gates are the value; the paper is markdown; there is no framework.
- Both metrics are **re-runnable and objective** (coverage %, reproduce-rate) — so we can
  test "workflow vs no-workflow" against ground truth, not judge-taste. That is the one
  discipline from the whole arc worth keeping: **prove it with a re-runnable metric.**

### The honest test
Same topic, paper written **with the gated loop** vs **freehand by the same agent**.
Score both arms with the held-out eval, not with the author-facing gates. Measure independent
position coverage, steelman fidelity, objection robustness, claim completeness and honesty,
reproduce-rate, and blind referee judgment. If the gated loop does not beat the freehand arm on
the independent scorecard without introducing a new kill-criterion, it has not earned its cost.
